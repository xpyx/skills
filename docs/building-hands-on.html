01 — THE PROBLEM

Eight months of directing, and the muscle goes quiet

After eight months working almost entirely by commanding agents, the worry isn't productivity. It's that you slowly become a reviewer who can no longer evaluate what he's reviewing.

The trap is specific. Agents produce voluminous, plausible code. Catching what's wrong with it takes deep system understanding — the kind you build by writing code, struggling with design tradeoffs, and debugging your own mistakes. Delegate the authoring entirely for long enough and the judgment that made you a good reviewer quietly decays, with nothing signalling the decline until something expensive gets through.

So: write code by hand again, deliberately, even though it's slower. But not all code — writing a migration or wiring a route teaches nothing. The goal is a working split: the agent does what doesn't teach you, you do what does.

That's the whole idea. Everything below is the work of making an agent actually honour it under pressure.

Agent writes

  • Scaffolding and wiring, imports, config
  • Migrations, type and DTO definitions
  • Test harnesses, fixtures, builders
  • CRUD passthrough, serialization
  • Repetitive transforms, build and CI config
  • Error plumbing — propagation, logging

You write

  • Domain rules and invariants
  • Algorithms and non-trivial control flow
  • State machines, concurrency decisions
  • Error semantics — what counts as an error
  • The shape and naming of the domain API
  • The choice of data model

Two tests decide any case the lists don't cover. The bug test: if this were wrong, would the bug be a typo or a misunderstanding? Misunderstanding means it's yours. The teaching test: would writing this teach you something you don't already know? No means it's the agent's.

02 — WHAT WE WEIGHED

Four decisions, each with a real alternative

Every one of these could have gone another way, and the rejected options weren't strawmen. Here's what was on the table and what each choice cost.

DECISION 01 — Who decides which parts the agent scaffolds and which you write?

Chosen

Agent proposes, you approve

It reads the task, proposes a written split with reasoning, and waits. The proposal itself teaches — you see how it decomposes the problem before agreeing.

Rejected

Fixed category rules

A rulebook applied without negotiation. Predictable and fast, but rigid the moment a task doesn't fit the categories.

Rejected

You declare the line

You say what you're keeping; the agent never touches it. Maximum control — but you lose the practice of decomposing, which is itself a skill.

The cost

Every task now opens with a negotiation round before any work happens. We bought a teaching moment and paid for it in latency — and in a gate the agent can drift past, which turned out to need three separate hard rules to hold shut.

DECISION 02 — What state is your part in when the agent hands it back?

Chosen

Failing tests + empty signature

Signature, types, and a full red suite pinning the behaviour including edge cases. You make it green. "Done" is unambiguous, and a good suite is itself instruction.

Rejected

Contract, no tests

You write the tests and the code. Maximum learning — test design is where most engineers are weakest — but slower, and "done" gets fuzzy.

Rejected

Contract + approach menu

The agent lays out 2–3 implementation approaches with tradeoffs and stops. You pick one, then write it yourself.

The cost, and the mitigation

Agent-written tests can smuggle in the agent's implementation and walk you down its path. Two countermeasures went into the skill because of this: the tests must be behavioural only — no mocking internals, no asserting call order — and the agent shows you the test names first and stops, so spotting the missing edge case stays your job. That name-list gate is what preserves the test-design practice the rejected option would have given you outright.

DECISION 03 — You're stuck and you ask for help. What is the agent allowed to give you?

Chosen

Escalating hint ladder

Four rungs, never skipped: a question back · name the concept · a worked example in a different domain · pseudocode. Real code only on an explicit override phrase, which is logged.

Rejected

Socratic only, forever

Questions and doc pointers, never an example. Purest learning — and genuinely maddening when you're stuck on something unfamiliar rather than half-known. Frustration is what makes people abandon a practice.

Rejected

Free help, logged after

Ask and get a real answer; the log surfaces the pattern later. Low friction, but relies entirely on your own honesty with the log.

The cost

The ladder makes caving a deliberate act rather than a slide — but it also means the agent will sometimes be less useful than it could be, on purpose, while you're tired. The override exists precisely so that's your call and not a fight with your tooling. This decision is also the one the evidence later rewrote completely; see reversal 01.

DECISION 04 — Your tests go green. What happens next?

Chosen

Review + persistent log

A senior-style critique that never edits your code, then an entry appended to a cross-repo log: what you owned, which rungs you climbed, overrides used, recurring themes.

Rejected

Review only, no log

Same critique, nothing written down. Keeps the repo clean and avoids a file that rots — but pattern-spotting relies on memory.

Rejected

Green is done

Tests pass, move on. Fastest, and it loses the layer where most growth happens — passing tests say nothing about whether what you wrote is any good.

The cost

The log lives at ~/.agents/learning-log.md — deliberately central rather than per-repo, because a theme like "mutation vs. return" only becomes visible when eight months of entries sit in one file. The tradeoff is a file outside version control that can rot if unused. Over time that log is the actual product of the skill; every phase upstream just feeds it.

03 — TWO MORE CALLS

The name, and how much enforcement to build

Naming

Candidates split into two families. Plain-stance names said what you're doing: hands-on, my-turn, manual-mode, stay-sharp. Role metaphors encoded the contract in one word: caddy (carries your bag, reads the green, recommends a club — never swings), sous-chef, belay, spotter, pit-crew.

The argument for a metaphor was real: a skill file that opens with "you are the caddy" gives the agent a role to reason from, which holds up better under pressure than a list of don'ts. hands-on won anyway, on the grounds that a name you'll type at 6pm should say what it does. The role-framing benefit was recovered elsewhere — in hard rules written as positive recipes rather than prohibitions.

Packaging

Three options. A: everything in one SKILL.md — simplest, but the split heuristic, hint ladder, review checklist and log format would all load every time even when only one phase is active. B: a lean main file plus per-phase reference files. C: B plus a PreToolUse hook that hard-denies edits to the files you claimed.

We shipped B and deliberately deferred C. Everything in B is instructions, and instructions drift — "don't write the core logic" is exactly the rule a helpful agent breaks at 6pm when it's so close. A hook can't be rationalized around. But locking in an unproven boundary just creates a fight with your own tooling, so the hook waits until the line has proven itself over real sessions. The groundwork is laid: the log's split: block is machine-readable precisely so the future hook can read which paths to deny itself.

04 — METHOD

Test-driven development, applied to a document

The core discipline: if you didn't watch an agent fail without the skill, you don't know whether the skill teaches the right thing.

So the build ran red-green-refactor, with prose in place of code. Six pressure scenarios were written first. Each was run against a fresh agent with no skill in context to establish a baseline — the RED. Only then was the skill written, aimed at the failures actually observed. Then the same scenarios re-ran until they passed.

This sounds like ceremony. It isn't: four of the six scenarios produced results that contradicted the plan, and every one of those contradictions changed the shipped file. A skill written from intuition would have been confidently wrong in four places.

01SPLITTwo-column proposal + reasoning. Gate: you approve or move the line.
02TESTSTest names first, then red tests + signature. Gate: you approve the list.
03YOUR TURNSilence. Hints only on request, one rung at a time.
04REVIEWCritique, no edits. You apply or push back.
05LOGEntry appended to the cross-repo learning log.

The phase machine exists because of one specific failure mode: momentum. An agent proposes a split, hears "ok", and carries straight through to writing your function, because continuing is an agent's default state. Each phase therefore ends with a question rather than with work.

05 — REVERSALS

What the evidence overturned

These are the four places where running the test first changed the product. Presented in the order they broke.

REVERSAL 01Agents don't cave. They over-help.

The plan assumed the phase-3 failure was an agent giving in and writing your code under pressure. Both baseline runs — including a hardened one with every trace of the rule stripped from the setup — refused to write the implementation, unprompted.

What it did instead, faced with "I've been on this 40 minutes, just write it":

expiresAt null handling · best-vs-first qualifying tier · the >= boundary · the percentOff scale · the zero-floor clampFive hints, one message. The solution's entire decision surface.

The user could not have failed to solve it afterwards, and would have learned nothing from the process. That reclassifies the failure from a discipline problem to a shaping problem — and the two need opposite treatments. A prohibition invites negotiation, and the baseline agent performed exactly that negotiation, hedging its hints as questions and calling them "the usual suspects." So the hint ladder is written as a positive recipe: a phase-3 reply IS the rung number, then that rung's content, then nothing else. The line that does the work says five hints at once is not rung 2 delivered thoroughly — it's the failure, regardless of how each hint is phrased.

REVERSAL 02The plan asserted a bug that didn't exist. Twice.

The review scenario was built around a mutation bug: user code that sorts the tiers array in place. The baseline agent didn't report it — because filter returns a fresh array, so the sort mutates nothing the caller can see. The agent was right and the plan was wrong.

The scenario was rewritten around the two real defects. Then the final review caught the same class of error again in the rewrite: one of those "real defects" — a hardcoded 'EUR' instead of order.subtotal.currency — is unreachable, because the fixture types currency as the literal 'EUR', giving it exactly one possible value. Two false premises, both authored by the planner, both caught by something other than the planner.

The shipped skill now produces agents that volunteer the correction: in every run, it names the real defect and explicitly clears the false lead rather than repeating it.

REVERSAL 03One whole feature had no problem to solve.

The decline condition — the skill refusing itself for chores — was specified as a required behaviour. The baseline never failed it. Agents recognise a bulk rename as mechanical and decline the ceremony unprompted, in both the original and hardened setups.

It shipped anyway, because the spec called for it and the spec is the binding authority. But it shipped as one line instead of a section, with the reasoning recorded: it's there on authority, not on evidence. The same call was made for the anti-mocking constraints on phase-2 tests — the baseline agent wrote clean black-box tests with no prompting at all, so those constraints compressed to a line and the emphasis went to the part that did fail: skipping the name-list.

REVERSAL 04Four rationalizations nobody ever made.

Skills that enforce discipline carry a table of excuses and rebuttals. Four rows were drafted from intuition during planning — including the very plausible "It's faster if I write this part."

All four were cut. That sentence appears nowhere in any transcript; no agent ever said it. Another draft row, "They said they'd read it carefully," turned out to appear only as the agent's own rebuttal to the user, never as its excuse.

The rule adopted: an invented rationalization teaches an agent an excuse it didn't have. Every row in the shipped table is quoted from a recorded run, and the reviewer verified each citation against the transcript character by character.

06 — THE RECURRING BUG

A documentation failure mode worth naming

One defect regenerated five times across two files, and it's the most transferable thing we learned.

The main file holds five hard rules. The per-phase reference files must cite those rules, never restate them — otherwise editing a rule leaves a stale copy behind in a file nobody thinks to open.

It kept coming back, because a restatement reads as helpful emphasis at the moment of writing. First it appeared verbatim. Told to delete the exact strings, the next round replaced them with paraphrases. Told again, in principle, it produced a different paraphrase. It only stopped when the fix message supplied the literal replacement sentences — and then it appeared again, unprompted, in the next file written.

The test that finally made it checkable, and which any reviewer can apply mechanically:

The drift test

If someone edited this rule in the canonical file, would this other file still be correct without the same edit?

The useful distinction underneath it: describing what a phase's output IS belongs in the reference file and can never go stale. Asserting what must not appear is the rule's job, and any copy of it will drift. That framing ended a problem three rounds of good intentions hadn't.

08 — KNOWN GAPS

What isn't verified, stated plainly

All of this is recorded in the repo under "Not yet tested", so it can't quietly disappear.

  • UntestedPhase 5 has no scenario at all. Nothing verifies an entry actually lands in the learning log in the documented schema — and the spec calls that log the real product of the skill.
  • UntestedThe ladder is verified only at rung 1. Escalation from 1→2→3, and the refusal to skip rungs, has never been exercised across multiple turns.
  • UntestedThe review override's second half. Every run ends at the confirmation question; the apply-and-log path has never executed.
  • UntestedReference self-loading. Every test run has the phase's reference file pre-loaded, so nothing verifies an agent chooses to open it on its own — arguably the riskiest real-world step.
  • DeferredThe enforcement hook. Waiting on real-world use before mechanically denying edits to claimed paths.
  • Tight780 of an 800-word budget in the main file. The budget is a judgement call, not an enforced limit — but the next rule added will need room made for it.
09 — TAKEAWAYS

What transfers, if you build one of these

  • Watch it fail first. Four of six scenarios contradicted the plan. Writing guidance from intuition would have shipped four confident errors, each one aimed at a problem nobody had.
  • Classify the failure before choosing the form. Discipline failures — knowing the rule and breaking it — take firm prohibitions. Shaping failures — complying with the wrong-shaped output — take a positive recipe, because a prohibition is something an agent can negotiate with.
  • Quote, never invent. A rationalization table built from imagination teaches excuses that didn't exist. Cite every row to a real transcript, and have someone verify the citations.
  • Cite rules, don't restate them. Apply the drift test to every cross-file reference. This is the failure that recurs hardest, because a restatement always looks like helpfulness at the moment you type it.
  • Keep the evidence in the repo. Twice, proof that the thing worked existed only in a scratch directory scheduled for deletion. Verification you can't show later isn't verification.
  • Let the artifact decline itself. A learning tool that insists on being used for chores is one you'll stop reaching for. Knowing when not to apply is part of the design, not an afterthought.

The last one generalises past skill-writing. The point was never to be faster than the agent — it's to stay the person who can tell when the agent is wrong.
