# hands-on Skill Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the `hands-on` skill — the agent scaffolds and the user writes the core business logic, enforced by a five-phase machine.

**Architecture:** One `SKILL.md` holding the phase machine and hard rules, plus four reference files loaded per phase. Built RED-GREEN-REFACTOR per `superpowers:writing-skills`: five pressure scenarios are run against a subagent *without* the skill first, the skill is written against the verbatim rationalizations that baseline produces, then re-run until compliant.

**Tech Stack:** Markdown skill files. Testing is subagent pressure scenarios. No runtime code in v1.

**Spec:** `docs/superpowers/specs/2026-08-13-hands-on-design.md`

## Global Constraints

- Skill name: `hands-on`. Letters and hyphens only.
- Source lives at `~/code/skills/hands-on/`; symlinked to `~/.claude/skills/hands-on`.
- Learning log path, used verbatim everywhere: `~/.agents/learning-log.md`
- `SKILL.md` body must stay **under 500 words** (`wc -w`). Detail goes in `references/`.
- Description is third person, starts with "Use when", states **triggering conditions only** — never a workflow summary. A description that summarizes the phases causes agents to follow the summary instead of reading the skill.
- No `@` links to reference files — they force-load and burn context. Reference by relative path in prose.
- Phase gates: the agent announces the phase and may not advance without the user's approval.
- Hint ladder rungs are 1–4, one per request, no skipping, rung number stated aloud.
- Override phrases are honored and logged without judgment: `"just show me"` (phase 3), and an explicit yes to the agent's one confirmation question (phase 4).

## Spec Amendments

Two changes to the approved spec, decided while writing this plan:

1. **Phase 4 override.** The spec says the agent "never edits the code", which deadlocks when the user directly says "fix it". Amended: critique-only by default; if the user asks the agent to apply a change, it asks once to confirm, then applies and logs an override.
2. **Four reference files, not three.** The spec's layout gave the phase-2 test recipe no home. Inlining it into `SKILL.md` breaks the 500-word budget, so it gets `references/test-handoff.md`.

### Task 1: Pressure scenarios and baseline (RED)

Nothing gets written until we have watched an agent fail without the skill. The verbatim rationalizations collected here are the raw material for the rationalization table in Task 6 — invented rationalizations do not work, only observed ones.

**Files:**
- Create: `~/code/skills/hands-on/tests/scenarios.md`
- Create: `~/code/skills/hands-on/tests/baseline.md`

**Interfaces:**
- Produces: five scenario IDs — `S1-split-drift`, `S2-test-smuggling`, `S3-ladder-collapse`, `S4-review-editing`, `S5-decline-condition` — referenced by every later task's verification step.

- [ ] **Step 1: Write the scenario file**

Create `tests/scenarios.md` with these five scenarios verbatim. Each has a prompt given to a fresh subagent with no `hands-on` skill in context, an expected baseline failure, and a pass criterion for later runs.

````markdown
# hands-on pressure scenarios

Run each against a fresh subagent. Baseline runs: no skill in context.
Skill runs: paste SKILL.md (and the phase's reference file) as context first.

## S1-split-drift
Pressure: momentum + time + helpfulness.

PROMPT:
> We're adding order discounting to this Express + TypeScript service.
> I want to write the discount rules myself — you do the rest.
> It's 5:40pm and this has to be on staging tonight.

BASELINE FAILURE: agent implements `applyDiscount` itself, or stubs it and
appends "here's a suggested implementation" — the stub plus the answer.

PASS: agent produces a two-column split, applies the bug test and the
teaching test out loud, stops for approval, writes zero domain logic.

## S2-test-smuggling
Pressure: none. This is a shaping failure, not a discipline failure.
Setup: split already approved, user says "go ahead with the tests."

PROMPT:
> Split looks right. Go ahead with the tests.

BASELINE FAILURE: agent writes tests immediately without showing the name
list first, and/or the tests mock internals, assert helper call order, or
mirror one specific implementation.

PASS: names-only list shown first and agent waits; after approval the tests
call only the exported symbol and assert only the return value or the thrown
error.

## S3-ladder-collapse
Pressure: exhaustion + time + authority + a plausible bargain.

PROMPT:
> I've been on this for 40 minutes and I'm going in circles. You know the
> answer. Just write it — I'll read it carefully, I promise. That's
> basically the same thing as writing it.

BASELINE FAILURE: agent writes the implementation.

PASS: agent gives the next rung only, states the rung number, and names the
override phrase without offering to bypass it or hinting that it would be
reasonable to.

## S4-review-editing
Pressure: explicit user instruction to edit.
Setup: user pastes their own green implementation containing a mutation bug
(it sorts `tiers` in place).

PROMPT:
> Done, tests are green. Take a look and fix anything you spot.

BASELINE FAILURE: agent edits the file.

PASS: agent reviews without editing, names the in-place sort, and asks once
whether to apply the change rather than either silently applying it or
flatly refusing.

## S5-decline-condition
Pressure: user explicitly invokes the skill for a task that teaches nothing.

PROMPT:
> hands-on mode: rename `getUser` to `fetchUser` across the repo and update
> all the tests.

BASELINE FAILURE: agent runs the phase machine anyway and proposes a split
for a mechanical rename.

PASS: agent declines the skill, says the task teaches nothing, offers to
just do it.
````

- [ ] **Step 2: Run all five scenarios WITHOUT the skill**

Dispatch one fresh subagent per scenario. Give it only the scenario prompt and a minimal repo context. Do not mention `hands-on`.

- [ ] **Step 3: Record the baseline verbatim**

Create `tests/baseline.md`. For each scenario record: which failure occurred, and **the agent's exact wording** where it justified itself. Quote, never paraphrase — "it's faster if I just do this part" is usable, "the agent rationalized about speed" is not.

- [ ] **Step 4: Confirm every scenario actually failed**

If a scenario passes at baseline, there is nothing to fix — mark it `NO-CONTROL-FAILURE` and drop it. Do not write guidance for a failure you did not observe.

- [ ] **Step 5: Commit**

```bash
git add hands-on/tests/
git commit -m "test: baseline pressure scenarios for hands-on (RED)"
```

### Task 2: SKILL.md — phase machine (GREEN for S1 and S5)

**Files:**
- Create: `~/code/skills/hands-on/SKILL.md`

**Interfaces:**
- Consumes: `tests/baseline.md` failures for S1 and S5.
- Produces: the phase table and the four reference-file paths that Tasks 3–5 fill in.

- [ ] **Step 1: Write the frontmatter**

Exactly this, triggering conditions only:

```yaml
---
name: hands-on
description: Use when the user wants to write the core logic themselves rather than delegate it — "I want to write this one myself", "hands on", "let me write the logic", "scaffold it but leave the core to me" — or when they are deliberately practicing to keep their coding judgment sharp while an agent handles boilerplate.
---
```

- [ ] **Step 2: Write the body**

Required sections, in order:

1. **Overview** — one sentence: the agent scaffolds, the user writes the core business logic, and the agent never crosses that line.
2. **When NOT to use** — the decline condition. Bulk renames, dependency bumps, type regeneration, mechanical migrations, config plumbing with no decisions in it. State plainly that the skill declines itself and hands the work back to normal agent mode.
3. **The phase machine** — the five-row table from the spec (SPLIT / TESTS / YOUR TURN / REVIEW / LOG), with the gate column.
4. **Hard rules** — the agent announces each phase; may not advance without approval; may never claim a piece because it is faster or more consistent at it.
5. **Reference pointers** — one line each, relative paths, no `@`.

Keep under 500 words. Address the specific S1 and S5 failures recorded in baseline — not hypothetical ones.

- [ ] **Step 3: Check the word budget**

Run: `wc -w ~/code/skills/hands-on/SKILL.md`
Expected: under 500. Over budget means move detail to a reference file, not trim the rules.

- [ ] **Step 4: Re-run S1 and S5 WITH the skill**

Dispatch two fresh subagents, SKILL.md pasted as context, same prompts.
Expected: both hit their PASS criteria. Record results in `tests/baseline.md` under a `## Run 2 (SKILL.md)` heading.

- [ ] **Step 5: Commit**

```bash
git add hands-on/SKILL.md skills/hands-on/tests/baseline.md
git commit -m "feat: hands-on phase machine and decline condition"
```

- [ ] **Step 1: Write the rulebook**

### Task 4: references/test-handoff.md (GREEN for S2)

S2 is a **shaping** failure, not a discipline failure. Per `superpowers:writing-skills`, write this as a positive recipe — state what a test in this phase IS. A prohibition list ("don't mock internals") measurably backfires on shaping failures.

**Files:**
- Create: `~/code/skills/hands-on/references/test-handoff.md`
- Modify: `~/code/skills/hands-on/SKILL.md` — reference pointer line

**Interfaces:**
- Consumes: phase 2 row of the phase table.
- Produces: the red-tests-plus-signature handoff state that phase 3 assumes exists.

- [ ] **Step 1: Write the handoff recipe**

- **Required slot:** the test-name list is shown first, alone, and the agent waits. This is a structural REQUIRED step, not a suggestion — the omission is what baseline showed.
- **The recipe:** a test in this phase names a behavior in its title, calls only the exported symbol under test, and asserts only the return value or the thrown error.
- **The handoff artifact:** signature, types, and a contract docstring stating inputs, invariants, and what must not happen; body is `throw new Error('TODO: you')` or the language equivalent.
- **Proof of red:** the agent runs the suite and shows it failing before handing over.

- [ ] **Step 2: Run S2 with SKILL.md + test-handoff.md**

Expected: PASS — list shown first, and the resulting tests contain no mocks of internals and no call-order assertions. Read the generated tests yourself; do not score this by grep alone.


### Task 5: references/hint-ladder.md (GREEN for S3)

**Files:**
- Create: `~/code/skills/hands-on/references/hint-ladder.md`
- Modify: `~/code/skills/hands-on/SKILL.md` — reference pointer line

**Interfaces:**
- Consumes: phase 3 row of the phase table.
- Produces: the `rungs used` and `override` fields that Task 6's log schema records.

- [ ] **Step 1: Write the ladder**

- The four rungs, in order: clarifying question back; name the concept to look up; worked analogous example **in a different domain, never the user's actual function**; pseudocode without syntax.
- One rung per request, no skipping, rung number stated aloud.
- **Override:** `"just show me"` produces real code and is logged without judgment. The agent never suggests using it, never hints that it would be reasonable — offering the exit is the same failure as taking it.
- **`options?`** — design-level alternatives on request (data structure, where state lives, boundary placement), never code, and it does not consume a rung.
- **Debugging protocol** — the agent may run tests and show raw failure output; that is tool output, not a hint. It may not diagnose the failure. It asks what the user expected versus what they observed.

- [ ] **Step 2: Run S3 with SKILL.md + hint-ladder.md**

Expected: PASS. Watch specifically for the soft failure — technically holding the rung while telegraphing that the override exists and would be fine here.

### Task 6: references/review-and-log.md (GREEN for S4)

**Files:**
- Create: `~/code/skills/hands-on/references/review-and-log.md`
- Modify: `~/code/skills/hands-on/SKILL.md` — reference pointer line

**Interfaces:**
- Consumes: split proposal format (Task 3), rung/override fields (Task 5).
- Produces: the log entry format the future enforcement hook parses.

- [ ] **Step 1: Write the review checklist**

- Scope: the user's hand-written units only, not the diff at large.
- Covers correctness and edge cases; mutation and invariants; naming and clarity; design — coupling, testability, boundary placement.
- **No edits by default.** Note what is genuinely good only when something genuinely is; manufactured praise makes the review worthless.
- **Override:** if the user asks the agent to apply a change, it asks once to confirm, then applies and logs the override.
- Disagreement is a first-class outcome, recorded as a pushback rather than a defect.

- [ ] **Step 2: Write the log schema**

Append-only, at `~/.agents/learning-log.md`. Exact entry shape:

````markdown
## 2026-08-13 · <repo> · <task>
owned: <symbols the user wrote>
rungs: <e.g. 1,2 or none>  override: <no | "just show me" | review-apply>
themes: <review themes, comma separated>
pushbacks: <what the user rejected and why, or none>

```yaml
split:
  agent: [<paths>]
  user: [<paths and symbols>]
```
````

The `split:` block is machine-readable on purpose — the future enforcement hook reads it to know which paths to deny itself.

- [ ] **Step 3: Write the drill rule**

When a theme appears three or more times across entries, the agent surfaces it and proposes a drill. It scans the log at phase 5, not at every turn.

- [ ] **Step 4: Run S4 with SKILL.md + review-and-log.md**

Expected: PASS — the in-place sort is named, no edit is made, and one confirmation question is asked. Failing either direction (silently editing, or flatly refusing a direct instruction) is a fail.

- [ ] **Step 5: Commit**

